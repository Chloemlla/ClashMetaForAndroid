## 二、SKILL.md 审查

### 2.1 目的与范围

一个遗留代码/高技术债/"屎山"代码库的治理技能。核心主张：**代码行数 (LOC) 是首要导航指标**，可读性和可维护性次之；指标决定先读哪里，代码和运行证据证明问题。

覆盖范围：小范围清理、死代码与命名噪音删除、完整问题盘点与评分、安全可靠性性能、测试交付、架构现代化、重写退役、旧接口旧数据兼容迁移。

### 2.2 八大不变量

1. **写穿式记录** — 发现即写入报告，不得扫描后凭记忆汇总
2. **完整列举** — 范围内所有 Critical/High/Medium/Low/Info 项完整记录；相同根因可聚类，但每个不同问题保留独立 ID，重复位置完整列出
3. **事实分层** — 仅用 `Confirmed`（有代码/命令/测试/运行数据/契约支持）和 `Suspected`（依赖产品意图/未知消费者/运行证据/用户裁决）；不得用置信度替代
4. **保护功能契约** — 先提取功能标准（文档/测试/示例/CLI help/schema/消费者），再判断代码；现有 bug ≠ 正确行为，但文档列出的功能不得以清理名义删除
5. **授权后实施** — 检查/解释/方案请求只读；修改必须在选定档位内，公开契约/真实数据/不可逆操作受硬门禁保护
6. **规模自适应** — 小问题紧凑记录；系统地图/迁移状态机仅用于跨模块/契约/数据/系统级问题
7. **文档闭环** — 行为/接口/术语/架构/运维变更需同步更新权威文档；缺少文档本身作为 Info 发现
8. **双快照** — 任何代码修改保留不可覆盖的 Before 基线，记录 After、差值和解释

### 2.3 齿轮系统

| 齿轮 | 含义 | 选项 |
|------|------|------|
| **任务规模** | 过程开销控制 | 轻量 / 标准 / 系统 |
| **E** 执行节奏 | E0 仅报告（审计默认）、E1 先报告后修复（标准/系统默认）、E2 同轮修复 |
| **G** 治理范围 | G0 仅体检、G1 局部修复（处理默认）、G2 渐进重构、G3 深度现代化、G4 重建/替换/退役 |
| **Q** 清理深度 | Q0 仅盘点、Q1 定点清理（轻量默认）、Q2 彻底清理（"全面清理"默认）、Q3 深度收缩 |
| **C** 兼容策略 | C0 严格、C1 向后兼容（默认）、C2 过渡、C3 允许破坏 |
| **D** 数据策略 | D0 不改数据、D1 原地兼容演进、D2 可逆迁移、D3 可重置/不可逆迁移 |

G 和 Q 独立：小型仓库全面清理 = `G1/Q2`，不会自动升级到 G2。
G3/G4/Q3/C2/C3/D2/D3 未获授权时只能作为方案，不得实施。

### 2.4 六步执行流程

1. **建立边界与报告** — 阅读仓库文档、验证环境、创建报告骨架、运行最小构建/测试/静态检查、运行清单脚本、冻结 Before 基线
2. **扫描并写穿发现账本** — 按 LOC/形状→可读性→可维护性→逻辑正确性→其他维度；分配 F-XXX ID；Compact 记录 Low/Info
3. **消解不确定性** — 通过仓库证据/历史/引用搜索/可运行验证将 Suspected 转为 Confirmed/Rejected；剩余依赖用户裁决项一次性提问
4. **排序并选择处理路线** — E0 到此进入总结；E1 冻结修复前章节等待确认；E2 可继续但每项必须有 Before 证据
5. **实施、验证与反哺文档** — E2 轻量分支做可回滚修复；标准/系统做代表性切片再扩展；bug 增加回归测试
6. **评分与对话总结** — 7 维度 0-10 分 + Overall；严格 10 格条形图

### 2.5 硬门禁

以下情况必须停止实施并请求确认：
- 升级到 G3/G4 或 Q3
- 升级到 C2/C3、缩短兼容窗口、删除公开 API/事件字段/配置键/数据库列/旧客户端支持/历史记录
- 升级到 D2/D3、接触真实数据或执行不可逆迁移
- 删除文档/测试/示例/外部消费者仍声明的功能
- 无法判断旧路径/`v2`/`legacy` 命名是否承载产品语义或外部契约
- 引入新运行基础设施、付费服务、跨团队契约或生产切流
- 无法建立与风险相称的备份/恢复/验证/回滚路径

## 四、6 个 Playbook 参考文件审查

### 4.1 逐个分析

#### cleanup-playbook.md — 代码清理手册
- **内容：** 9 步固定检查顺序（LOC 统计→读最大单元/热点/关键路径→可读性→可维护性→验证逻辑→清单重复/死代码/依赖/配置分叉→写穿账本→按 Q 深度实施）
- **亮点：** "保护契约，不保护 bug"原则；严格 Suspected/Info 纪律
- **问题：** 与 `audit-code-design.md` 大量主题重叠（LOC/形状、可读性、可维护性、正确性、重复/死代码/配置分叉）；检查-行动拆分合理但两个文件必须保持同步——有漂移风险

#### treatment-playbook.md — 渐进治理方法手册
- **内容：** 6 步治理顺序（止血→恢复构建/测试/发布/回滚→可观测性+行为基线→隔离热点/外部依赖→修复边界/所有权/模型→删除旧路径/兼容/切换）、6 种安全网选项、制造接缝技术、局部设计治理循环、模块/领域边界治理、大规模替换模式（Strangler Fig/Branch By Abstraction/Parallel Change）、依赖升级、失败模式目录（10 种）
- **亮点：** 操作上最丰富；失败模式列表是很好的自查清单；"永久双轨"直接回答了 deep-modernization 的"临时双轨持续太久"风险
- **问题：** 与 `audit-tests-delivery.md` §1 安全网技术重叠

#### deep-modernization.md — 深度现代化、重建与退役决策
- **内容：** G3/G4 框架——可测量目标优先、6 路线决策表（保留/止血/渐进重构/重新架构/重建替换/退役）、G3 决策门禁（7 条件）、领域/目标架构 7 步骤、G4 重建门禁（证据阈值）、反大爆炸信号（6 种）、分段路线 A-E、停止与转向条件（7 种）
- **亮点：** "提前定义退出条件"和沉没成本纪律；G3 与 G4 的清晰分离
- **问题：** "R 类"缩写未内联定义（仅通过 methodology-sources 外部链接可解析）；6 路线（含止血）与 SKILL.md 的 G0-G4 档位无显式映射

#### compatibility-data-migration.md — 兼容与数据迁移手册
- **内容：** 兼容范围检查清单、兼容矩阵、Expand-Migrate-Contract 三阶段规则、9 状态数据迁移状态机（Planned→Expanded→Backfilling→Shadowing→Dual-compatible→Cutover-canary→Cutover-complete→Observing→Contracted）、迁移技术选择（离线/在线回填+CDC/应用双写/发件箱/收件箱/双读/读修复）、4 层对账（结构/数量/内容/业务）、回滚分类（代码 vs 路由 vs 数据 vs 业务补偿）、收缩检查清单（7 项）、高风险反模式（9 种）
- **亮点：** 状态机是整套中最精确的产出；回滚正确性洞察（旧代码无法表达新模型数据）和兼容方向性警告都很出色
- **问题：** 状态机状态与报告发现处置无映射；CDC/发件箱/双写都假设遗留代码库通常没有的基础设施（列出了要求但无引导顺序）

#### methodology-sources.md — 方法论来源与适用边界
- **内容：** 质量与安全（ISO/IEC 25010、OWASP ASVS、CISA Secure by Design）、渐进现代化（Fowler Strangler Fig/Branch By Abstraction/Parallel Change/Legacy Seam）、路线选择（Azure 云采用框架、AWS PG 大规模迁移指南）、开源工具索引（CodeQL、静态分析工具目录、Parallel Change 示例仓库）、技能特定约束（6 条）
- **亮点：** 诚实的范围声明（"不意味着正式符合或认证"）；明确的工具复用偏好；外部内容告知但不决定
- **问题：** 数据迁移技术（CDC、发件箱/收件箱、读修复、影子计算）和评分/排序公式无来源引用——"工程经验"条款覆盖但未列举哪些部分是项目原创；无日期/版本锁定 OWASP/CISA/ISO 引用

#### prioritization-and-report.md — 发现项排序、评分与报告模板
- **内容：** 发现模型（F-XXX ID、共享 ID 仅当相同根因/影响/建议）、严重度锚点（行为性，不能从 LOC/lint/工具默认值映射）、证据状态（Confirmed/Suspected）、反作弊计数规则（包含已修复/推迟/接受的项，修复不能消除发现计数）、Priority Index（可选细排序：I×L+B+H+R，四个波段）、7 维度质量评分（Security/Stability/Performance/Testing/Maintainability/Design/Release，0-10，Overall=等权算术平均，固定 10 格条形图）、写穿规则（7 条）、完整报告模板、主对话输出格式
- **亮点：** 计数规则和冻结 Before 设计使测量契约可审计且难以作弊；模板异常完整
- **问题：** Priority Index 无工作示例且无到定性严重度标签的正式映射；7 个评分维度与 8 个审计文件无显式映射（product-interface 和 evolution 无明确归属评分维度）；"正好 10 格字符"的强制要求是实施细节，不增加语义

### 4.2 总体评价

6 个 playbook 组成一个真正一致的系统：

```
SKILL.md (编排层: E/G/Q/C/D + 不变量 + 门禁)
    ├── 8 个 audit-*.md (检查标准: "找什么")
    ├── cleanup-playbook (Q 深度清理)
    ├── treatment-playbook (G2+ 渐进治理)
    ├── deep-modernization (G3/G4 决策门禁)
    ├── compatibility-data-migration (C/D 兼容与迁移)
    ├── prioritization-and-report (报告与评分)
    └── methodology-sources (外部方法校准)
```

**统一哲学：** 证据分诊先于行动（Confirmed vs Suspected）、可逆性作为一等要求、不超出授权扩大范围、写穿账本+冻结 Before 快照。

**矛盾：** 无硬矛盾。清理手册说"不假设当前行为正确"，治理手册说"特征测试冻结当前行为"——两者在各自文件中显式解决（先保护，再决定是否纠正）。

### 5.2 scripts/inventory_codebase.py

**功能：** 只读、语言无关的仓库清单生成器。默认只统计 `git ls-files` 跟踪的文件，失败时回退到 `os.walk`。

**逻辑流程：**
1. 选择源（git 跟踪文件 / os.walk 回退 / `--include-untracked` 强制遍历）
2. 排除（DEFAULT_EXCLUDES 目录名集合）
3. 每文件流水线：symlink 记录跳过 → 非文件跳过 → 获取大小 + 8KB 头读取 → 二进制检测 → 扩展名分组 → 测试/生成代码启发式分类 → 文本文件逐行流式处理（物理行+非空行+每扩展名行数+TODO/FIXME/HACK/XXX 标记扫描）
4. 聚合：3 个源类别（first_party_production / tests / generated_or_vendored）
5. 输出：JSON（`--format json`）或 Markdown

**发现的问题：**

| 严重度 | 问题 | 说明 |
|--------|------|------|
| **High** | **Unicode `\b` 边界导致中文注释标记匹配失效** | 第 91 行 `\b(TODO|FIXME|HACK|XXX)\b`。Python 3 `\b` 是 Unicode 感知的，CJK 表意文字属于 `\w`，所以 `TODO修复`（标记后紧跟 CJK 字符，无空格/标点）**不会匹配**。应使用 ASCII 边界 `(?<![A-Za-z0-9_])(TODO|FIXME|HACK|XXX)(?![A-Za-z0-9_])` |
| Low | 构建缓存排除缺失 | `.gradle`、`bin`、`obj`、`.dart_tool`、`.cargo` 不在 DEFAULT_EXCLUDES 中。在遍历模式（`--include-untracked` 或非 git 根目录）下，Gradle 项目的 `.gradle` 缓存会被遍历 |
| Low | 测试文件正则有漏报 | 第 92-95 行第三个替代 `(_test\|_spec\|Test)\.[^/]+$` 要求点号紧接，所以 `foo_tests.py`、`my_test_helper.py`、大写变体 `FooTEST.kt` 都会漏报；`foo.test.js`（点号分隔）也会漏报 |
| Low | 无上限标记样本默认值 | `--max-marker-samples 0` 表示"保留全部"，大仓库上 Markdown 输出可能数千行 |

### 5.3 scripts/inventory_markdown.py

**功能：** 纯渲染器，无 CLI 无 main。将 `collect()` 的字典渲染为 Markdown 报告。

**输出内容：** 标题+摘要要点、代码行清单表、最大第一方生产源文件、N 行以上第一方源候选、语言和文件类型、最大文本文件（按物理行）、最大文件（按字节）、信号（标记总数/清单/CI/不可读文件/symlink 样本）、标记出现列表、脚注。

**发现的问题：**

| 严重度 | 问题 | 说明 |
|--------|------|------|
| Low | 测试文件/生成文件列表数据已收集但未渲染 | `collect()` 产生 `test_files`、`test_file_samples`、`generated_or_vendored_files`、`generated_or_vendored_samples` 专门用于显示，但 `markdown()` 从未渲染——只显示计数 |
| Low | 过长内联列表无分行处理 | `manifests` 和 `ci_files` 用 `", "` 连接在单行，多清单/CI 文件的仓库产生极长难读行 |
| Info | `format_bytes` 始终显示一位小数 | `512 B` 渲染为 `512.0 B`——无小数部分时 `.0` 是噪音 |
